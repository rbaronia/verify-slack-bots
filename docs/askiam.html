🤖 AskIAM

A Cloudflare Worker that answers natural-language IBM Verify IAM queries in Slack via the /askiam slash command. Every Slack user authenticates with their own IBM Verify identity through OAuth 2.0 Authorization Code + PKCE — tokens are cached in KV and auto-refreshed.

Live URL: askiam-bot.baronia.workers.dev Slack command: /askiam MCP server: mcp.baronia.work/mcp

Request Flow

/askiam count users
        │
        ▼
POST /slack/command  (Worker)
        │
        ├─ Token in KV for this Slack user_id?
        │
        ├── YES → routeQuery() → Gemini picks MCP tool + args
        │              └── callTool() → mcp.baronia.work (IBM Verify APIs)
        │                      └── answerQuery() → Gemini summarises → Slack Block Kit
        │
        └── NO  → generate PKCE challenge
                  store {userId, verifier, query, response_url} in KV (state:<nonce>, 5-min TTL)
                  reply with IBM Verify login link
                          │
                          ▼
                  User authenticates at baronia.verify.ibm.com
                          │
                          ▼
                  GET /oauth/callback?code=...&state=...
                          ├── Exchange code for access_token + refresh_token
                          ├── Store in KV under token:<slack_user_id>
                          └── Fire original query → result posted to Slack

Token Lifecycle

EventBehaviour
First /askiamNo token in KV → send IBM Verify login link (PKCE flow, 5-min TTL on state)
After loginToken stored in KV under token:<slack_user_id>
Subsequent queriesToken read from KV → query runs immediately
Access token rejected (401)Auto-refresh using stored refresh token; only writes to KV if token actually changed
Refresh token expiredDelete KV entry → prompt re-authentication

KV Write Optimisation (Free Tier)

Cloudflare's free tier allows 1,000 KV put operations per day. The worker uses three strategies to stay within this limit:

  • Deterministic result cache keys — pagination result cache keys use SHA-256(toolName + args) instead of a random suffix, so identical queries reuse the same KV slot instead of writing a new entry each time.
  • Cache read-before-write — before caching a paginated result, the existing entry is read. If the same data is already cached (TTL still valid), the put is skipped entirely.
  • Conditional token refresh — the refreshed token is only written back to KV if the access_token or refresh_token value actually changed, preventing duplicate writes from concurrent 401-refresh races.

Cloudflare Setup

The MCP server at mcp.baronia.work sits behind a geo-block firewall rule (blocks EU, NA, AF, SA). Cloudflare Workers egress from global PoPs and hit this rule. Two things are needed to allow the Worker through.

1 — Cloudflare Access service token

Creates a machine-to-machine credential the Worker sends on every MCP request so Cloudflare Access lets it bypass the geo-block.

  1. Zero Trust → Access → Service Auth → Service Tokens → Create Service Token
    Name: askiam-worker. Copy the CF-Access-Client-Id and CF-Access-Client-Secret (shown once).
  2. Zero Trust → Access → Applications → Add → Self-hosted
    Domain: mcp.baronia.work. Policy action: Service Auth → select the token above.
  3. Set both values as Worker secrets (CF_ACCESS_CLIENT_ID, CF_ACCESS_CLIENT_SECRET).

2 — WAF custom rule geo-block bypass

The geo-block WAF rule fires before Cloudflare Access evaluates service tokens, so a skip rule is also needed.

Cloudflare Dashboard → baronia.work → Security → WAF → Custom Rules → Create rule

FieldValue
Rule nameSkip geo-block for AskIAM Worker
Expressionhttp.request.headers["cf-access-client-id"][0] eq "<your-token-id>.access"
ActionSkip → All remaining custom rules
PositionAbove the "Block Access Outside of Asia" rule

IBM Verify Setup

Redirect URI

Add this redirect URI to the MCP Server Subject app in IBM Verify Admin Console → Applications → edit → Redirect URIs:

https://askiam-bot.baronia.workers.dev/oauth/callback

User entitlements

Every Slack user who runs /askiam must be entitled to the MCP Server Subject app:

Admin Console → Applications → MCP Server Subject → Entitlements tab → add user

Admin list

Write operations (password reset, user creation, etc.) are restricted to users in the admin list stored in KV under config:admin_users. Set it with:

npx wrangler kv key put --namespace-id=<ASKIAM_TOKENS_ID> \
  config:admin_users '["U12345678","U87654321"]'

Use Slack user_id values (not usernames). Users not in this list who attempt write operations receive a permissions error.

Slack App Setup

  1. Go to api.slack.com/apps → Create New App → From an app manifest
  2. Use the JSON tab — paste slack-app-manifest.json
  3. Install to workspace → copy Signing Secret → push as SLACK_SIGNING_SECRET
  4. Slash command request URL: https://askiam-bot.baronia.workers.dev/slack/command
  5. Interactivity request URL: https://askiam-bot.baronia.workers.dev/slack/action

MCP Protocol Notes

The IBM Verify MCP server uses MCP Streamable HTTP transport (spec 2024-11-05). Every session requires a two-step handshake:

  1. initialize — POST to /mcp with no mcp-session-id. Server returns a mcp-session-id response header. Requires a valid IBM Verify Bearer token.
  2. tools/call — POST to /mcp with the mcp-session-id from step 1.

Required headers on every MCP request:

HeaderValue
AuthorizationBearer <ibm_verify_access_token>
Content-Typeapplication/json
Acceptapplication/json, text/event-stream
personaadmin — exposes all IBM Verify tools
mcp-session-idSession ID from initialize (omit on the initialize call itself)
CF-Access-Client-IdCloudflare service token ID
CF-Access-Client-SecretCloudflare service token secret

Responses may be application/json or text/event-stream (SSE). The client handles both formats.
