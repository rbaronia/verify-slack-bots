AskIAM

Natural-language IBM Verify IAM queries via the /askiam Slack slash command. Each Slack user authenticates with their own IBM Verify identity through OAuth 2.0 Authorization Code + PKCE — tokens are cached in Cloudflare KV and auto-refreshed.

Request flow
/askiam count users
        │
        ▼
POST /slack/command  (Worker)
        │
        ├─ Token in KV for this Slack user_id?
        │
        ├── YES → routeQuery() → Gemini picks MCP tool + args
        │              └── callTool() → mcp.baronia.work (IBM Verify APIs)
        │                      └── answerQuery() → Gemini summarises → Slack Block Kit
        │
        └── NO  → generate PKCE challenge
                  store {userId, verifier, query, response_url} in KV  (state:<nonce>, 5-min TTL)
                  reply to Slack with IBM Verify login link
                          │
                          ▼
                  User authenticates at baronia.verify.ibm.com
                          │
                          ▼
                  GET /oauth/callback?code=...&state=...
                          ├── Exchange code → access_token + refresh_token
                          ├── Store in KV under  token:<slack_user_id>
                          └── Fire original query → result posted to Slack
Token lifecycle
Step 1

First /askiam

No token in KV. Worker generates a PKCE challenge, stores state in KV (5-min TTL), and replies with an IBM Verify login link.

Step 2

User authenticates

User clicks the link, signs in to IBM Verify. IBM Verify redirects to /oauth/callback with an auth code.

Step 3

Tokens stored in KV

Worker exchanges the code for access_token + refresh_token. Stored in KV under token:<slack_user_id>. Original query fires automatically.

Subsequent queries

Instant execution

Token read from KV → query runs immediately. On 401, auto-refresh using the refresh token. New tokens only written to KV if they actually changed.

KV write optimisation

Cloudflare's free tier allows 1,000 KV put operations per day. Three strategies keep the worker well within this limit:

StrategyDetail
Deterministic result cache keys Paginated result cache keys use SHA-256(toolName + args) instead of a random suffix — identical queries from the same user always map to the same KV slot instead of creating a new entry each time.
Cache read-before-write Before caching a paginated result, the existing slot is read. If the same data is still cached (TTL not expired), the put is skipped entirely — zero extra KV writes for repeated queries within the 10-min window.
Conditional token refresh The refreshed token is only written back to KV if access_token or refresh_token actually changed — prevents duplicate writes from concurrent 401-refresh races.
⚠️ If you hit KV 429 errors, the free-tier daily limit has been reached. The optimisations above prevent this under normal load. Heavy burst usage may require upgrading to the Cloudflare Workers Paid plan.

Cloudflare setup

The MCP server at mcp.baronia.work sits behind a geo-block WAF rule (blocks EU, NA, AF, SA). Cloudflare Workers egress from global PoPs that hit this rule. Two things are needed:

1 — Cloudflare Access service token

A machine-to-machine credential the Worker sends on every MCP request so Cloudflare Access lets it bypass the geo-block.

  1. Zero Trust → Access → Service Auth → Service Tokens → Create Service Token
    Name: askiam-worker. Copy the CF-Access-Client-Id and CF-Access-Client-Secret values — they are shown only once.
  2. Zero Trust → Access → Applications → Add → Self-hosted
    Domain: mcp.baronia.work. Policy action: Service Auth → select the token created above.
  3. Set both copied values as Worker secrets (CF_ACCESS_CLIENT_ID, CF_ACCESS_CLIENT_SECRET).

2 — WAF custom rule geo-block bypass

The geo-block WAF rule fires before Cloudflare Access evaluates service tokens, so a WAF skip rule must also be created.

Cloudflare Dashboard → baronia.work → Security → WAF → Custom Rules → Create rule

FieldValue
Rule nameSkip geo-block for AskIAM Worker
Expressionhttp.request.headers["cf-access-client-id"][0] eq "<your-token-id>.access"
ActionSkip → All remaining custom rules
PositionAbove the "Block Access Outside of Asia" rule
IBM Verify setup

Redirect URI

Add this redirect URI to the MCP Server Subject app in IBM Verify Admin Console → Applications → edit → Redirect URIs:

https://askiam-bot.baronia.workers.dev/oauth/callback

User entitlements

Every Slack user who runs /askiam must be entitled to the MCP Server Subject app:

Admin Console → Applications → MCP Server Subject → Entitlements tab → add user

Admin list

Write operations (password reset, user creation, MFA deletion) are restricted to users in an admin list stored in KV under config:admin_users. Set it with:

npx wrangler kv key put --namespace-id=<ASKIAM_TOKENS_ID> \
  config:admin_users '["U12345678","U87654321"]'

Use Slack user_id values (not display names). Users not in this list who attempt write operations receive a clear permissions error.

Slack app setup
  1. Go to api.slack.com/apps → Create New App → From an app manifest
  2. Use the JSON tab — paste slack-app-manifest.json from this repo
  3. Install the app to your workspace
  4. Copy the Signing Secret from Basic Information → push as SLACK_SIGNING_SECRET
  5. Slash command request URL: https://askiam-bot.baronia.workers.dev/slack/command
  6. Interactivity request URL: https://askiam-bot.baronia.workers.dev/slack/action
MCP protocol notes

The IBM Verify MCP server uses MCP Streamable HTTP transport (spec 2024-11-05). Every session requires a two-step handshake:

  1. initialize — POST to /mcp with no mcp-session-id. The server returns a mcp-session-id in the response header. Requires a valid IBM Verify Bearer token.
  2. tools/call — POST to /mcp with the mcp-session-id from step 1 plus the tool name and arguments.

Required headers on every MCP request:

HeaderValue
AuthorizationBearer <ibm_verify_access_token>
Content-Typeapplication/json
Acceptapplication/json, text/event-stream
personaadmin — exposes all IBM Verify MCP tools
mcp-session-idSession ID from initialize (omit on the initialize call itself)
CF-Access-Client-IdCloudflare service token ID
CF-Access-Client-SecretCloudflare service token secret
ℹ️ Responses may be application/json or text/event-stream (SSE). The mcp-client.js shared module handles both response formats transparently.
